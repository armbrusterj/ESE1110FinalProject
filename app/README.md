# DMXtra app

A SwiftUI app (iOS 17+ and macOS 14+, one multiplatform target) that controls the DMXtra
DMX controller over HTTP. The API it speaks is in [`../embedded/API.md`](../embedded/API.md).

The app deals only in DMX terms (fixtures, channels, addresses, the universe). Everything about
the patch comes from the controller (`GET /fixtures`, `GET /fixture-types`). A fixture type the
app has never seen still works: it gets one fader per channel, labelled with the channel name.

## Layout

```
app/
├── project.yml              XcodeGen spec (source of truth for the Xcode project)
├── DMXtra/
│   ├── DMXtraApp.swift
│   ├── Info.plist           written by XcodeGen from project.yml
│   ├── DMXtra-macOS.entitlements
│   ├── Model/               Codable models, patch maths, update throttle
│   ├── Networking/          ControllerClient actor, errors, address parsing
│   ├── State/AppModel.swift @Observable app state, polling, hold-back while editing
│   └── Views/               Fixtures, fixture control, patch editing, universe, controller
├── DMXtraTests/             Swift Testing unit tests (+ opt-in mock-server integration tests)
└── tools/mock_server.py     Mock controller, standard library only
```

## Generate the project

The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) and is **not
committed** (`app/DMXtra.xcodeproj/` is in `.gitignore`). `project.yml` is the source of truth, so
regenerate after pulling or after adding/removing files:

```bash
brew install xcodegen
```

```bash
cd app && xcodegen generate
```

Then open `DMXtra.xcodeproj` and pick the **DMXtra** scheme with a Mac or iOS Simulator destination.

## Run it

### Against the mock server (no board needed)

```bash
cd app && python3 tools/mock_server.py --port 8080
```

In the app, open the **Controller** tab and enter `127.0.0.1:8080` (Mac or iOS Simulator).

To reach the mock from a phone on the same WiFi, bind it to every interface and use the Mac's
IP address in the app:

```bash
python3 tools/mock_server.py --host 0.0.0.0 --port 8080
```

Options: `--latency 30` adds 30 ms to each request to feel more like the board; `--quiet` stops
the request log. The mock copies the firmware: default patch ("Wash 1" at 1, "Wash 2" at 4),
status codes and error messages, overlap rules, the 32-fixture limit (507), the 4096-byte body
limit (413), one connection at a time, and `Connection: close` on every response.

### Against the board

Enter the board's IP address (e.g. `10.103.210.50`) in the Controller tab. Port 80 is the default,
so no port is needed. The phone or Mac must be on the same network as the board.

The address is saved in `UserDefaults` and reconnected on launch. It can also be passed on the
command line, which is handy for the Mac build: `DMXtra.app/Contents/MacOS/DMXtra -controllerAddress 127.0.0.1:8080`.
Debug builds also accept `-DMXtraTab universe|controller` to open on that tab.

### Running on an iPhone

iOS uses automatic signing. Choose your team under *Signing & Capabilities* in Xcode (or add
`DEVELOPMENT_TEAM: XXXXXXXXXX` to the target settings in `project.yml`), then run on the device.
The first request triggers the iOS Local Network permission prompt; allow it.

## Command-line build and test

```bash
cd app && xcodebuild -project DMXtra.xcodeproj -scheme DMXtra -destination 'platform=macOS' test
```

```bash
cd app && xcodebuild -project DMXtra.xcodeproj -scheme DMXtra -destination 'generic/platform=iOS Simulator' build
```

Unit tests cover model decoding (using the JSON from API.md), the rate-limiting logic, and the
next-free-address calculation. The `MockServerIntegrationTests` suite drives the real
`ControllerClient` and `AppModel` against a running mock (or board). It is skipped unless
`DMXTRA_MOCK_URL` is set. Note that it changes the controller's state and ends with a blackout:

```bash
TEST_RUNNER_DMXTRA_MOCK_URL=127.0.0.1:8080 xcodebuild -project DMXtra.xcodeproj -scheme DMXtra -destination 'platform=macOS' test
```

## Info.plist and entitlements

All of these are set in `project.yml`:

| Setting | Why |
|---|---|
| `NSAppTransportSecurity` → `NSAllowsLocalNetworking = YES` | The controller speaks plain HTTP (no TLS). ATS blocks plain HTTP by default; this allows it for local-network hosts such as `.local` and unqualified names. |
| `NSAppTransportSecurity` → `NSAllowsArbitraryLoads = YES` | On campus WiFi the board is reached by a raw IP (e.g. `10.103.210.50`). This broader exception makes sure plain HTTP works to any address the user types, whether or not ATS treats it as local. |
| `NSLocalNetworkUsageDescription` | iOS asks the user before an app talks to devices on the local network. This is the text shown in that prompt. Without it, requests to the board fail on iOS. |
| `com.apple.security.app-sandbox` + `com.apple.security.network.client` (macOS only, `DMXtra-macOS.entitlements`) | The Mac app runs in the App Sandbox, which blocks networking unless the *Outgoing Connections (Client)* entitlement is present. |

The Mac build is ad-hoc signed ("Sign to Run Locally"), so it builds and runs without a team.

## How it talks to the board

The board handles one connection at a time and closes it after each response, so:

- **One request at a time.** Every call goes through the `ControllerClient` actor, which chains
  requests so each waits for the previous one to finish. Timeouts are 3 seconds. Errors become
  `ControllerError`, which carries the server's `error` message (shown for 409, 507, etc.).
- **Rate limiting.** Fader and color-picker changes are sent with `PATCH /fixtures/{id}` and
  `values`, with `null` for channels that didn't change. Each fixture sends at most about 20 updates
  a second. While an update is waiting, a newer value for the same channel replaces it (changes to
  different channels are merged), and the last value is always sent after the user lets go.
  (`ThrottleCore` and `FixtureUpdateThrottle` in `Model/UpdateThrottle.swift`.)
- **Polling.** While the Fixtures, fixture control, or Universe screens are visible, the app polls
  `GET /fixtures` every 2 seconds (the Universe screen also polls `GET /dmx`), so changes from other
  clients show up. Polls never overwrite a fixture that's being edited: updates for it are held back
  while a control is held, while an update is waiting or in flight, and for 1.5 s afterwards.
